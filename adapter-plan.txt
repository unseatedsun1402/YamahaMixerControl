› # Feature: Hardware Client Framework (MIDI, OSC, Mackie MCU Control)
  
  ## Context
  
  This project already implements a Yamaha digital mixer integration layer that communicates with desks such as the Yamaha M7CL using MIDI NRPN and SysEx messages.
  
  The existing architecture works as follows:
  
  1. Incoming Yamaha NRPN and SysEx messages are decoded.
  2. Mapping definitions convert protocol messages into internal control objects.
  3. Internal control objects represent mixer state (faders, mutes, sends, pans, EQ parameters, scene controls, etc).
  4. Control object changes are published through the application's event/update system.
  5. A web API and browser\-based client consume these updates and provide a bidirectional remote mirror of the connected mixer.
  6. Browser client changes are translated back into Yamaha NRPN/SysEx messages to update the desk.
  
  This architecture is already functioning correctly and should be treated as the source of truth.
  
  ---
  
  ## Goal
  
  Add support for hardware control surface clients and OSC clients without modifying the Yamaha protocol layer.
  
  Examples include:
  
  - Behringer X\-Touch
  - Mackie MCU Control compatible surfaces
  - Generic MIDI controllers
  - OSC\-based controllers
  - Future hardware control surfaces
  
  The implementation must reuse the existing internal control model so that all clients share the same mixer state.
  
  ---
  
  ## Architectural Requirements
  
  Do NOT create a second mixer model.
  
  Do NOT create direct Yamaha ↔ Mackie MCU mappings.
  
  Do NOT create Yamaha\-specific logic inside hardware client implementations.
  
  Instead implement a client adapter architecture:
  
  Yamaha Protocol → Internal Control Objects → Event Bus / State Layer → Client Adapters
  
  Client adapters both:
  
  - Receive state updates from the internal control layer.
  - Publish control changes back into the internal control layer.
  
  All clients must therefore mirror each other automatically.
  
  Example:
  
  Yamaha Desk Fader Move → Internal Control Updated → Browser UI Updated → X\-Touch Motor Fader Updated → OSC Clients Updated
  
  X\-Touch Fader Move → Internal Control Updated → Yamaha NRPN Generated → Browser UI Updated → OSC Clients Updated
  
  ---
  
  ## New Components
  
  ### IControlClient
  
  Create a common client interface.
  
  Responsibilities:
  
  - Connect
  - Disconnect
  - Subscribe to control updates
  - Publish control changes
  - Report capabilities
  - Report connection status
  
  Example client types:
  
  - WebClient
  - OscClient
  - Mackie MCUClient
  - GenericMidiClient
  
  ---
  
  ### Hardware Client Manager
  
  Implement a manager responsible for:
  
  - Client registration
  - Client lifecycle
  - Connection management
  - Broadcasting control updates
  - Capability discovery
  
  The manager should not know Yamaha details.
  
  It should only operate on internal control objects.
  
  ---
  
  ### Mackie MCU Control Adapter
  
  Create an adapter capable of communicating with:
  
  - Behringer X\-Touch
  - Mackie MCU Control Universal compatible devices
  
  Initial scope:
  
  - Motor faders
  - Mute buttons
  - Solo buttons
  - Bank switching
  - Channel selection
  
  Design the adapter to support future expansion.
  
  ---
  
  ### OSC Adapter
  
  Create an OSC client adapter.
  
  Requirements:
  
  - Configurable OSC server/client endpoints
  - Bidirectional operation
  - Subscribe to control updates
  - Publish incoming OSC commands into control changes
  
  OSC paths should be configurable rather than hard\-coded.

  12. Risks / things to verify during implementation
  
  - Registry-reload listener survival across wholesale registry swap. The context-gatherer flagged that MidiServer.onRegistryReloaded builds a brand-new CanonicalRegistry; the
  reload listener is attached to the original registry in the constructor. Verify that notifyReloadListeners fires on the in-place reloadMappings path (it does,
  CanonicalRegistry.java line ~337) and that the new-registry path in MidiServer.run() calls onRegistryReloaded directly (it does). The manager must register on the initial
  registry and re-register on each new registry it receives, since the new registry created in MidiServer.run() does not inherit the listener.
  - Control type information. ControlType/ContextType are UI-layer enums, not stored on ControlInstance. A Mackie encoder that needs to know "is this a fader or a mute" must
  infer from the group/subcontrol naming scheme (getGroup()/getSubcontrol()), as ControlSchema already does. Confirm the naming conventions for faders/mutes/solos/selects in
  the mapping files before writing the encoder.
  - Echo suppression correctness. The desk echoes a client-originated change back over MIDI → MidiProcessingLoop → updateValue (no thread-local origin) → dispatcher broadcasts
  to all clients including the originator. This matches the web path's behavior (the desk echo is a confirmation, and broadcastControlUpdate only suppresses the immediate web
  session, not the later echo). For motor faders this is harmless. Confirm during testing that re-entrant sends to the originating X-Touch don't cause jitter; if they do,
  suppress by comparing the outgoing value to the last sent value per control.
  - resolveCc is a stub (CanonicalRegistry.java returns null). Mackie uses Pitch Bend and CC, not NRPN/SysEx, so the Mackie decoder must resolve directly to canonical ids via
  its own bank map — it does not rely on CanonicalRegistry.resolveCc. Generic MIDI similarly maps CC directly. No need to fix resolveCc.
  - OSC listen-socket security. Document and enforce the loopback-only edit rule for non-loopback listen addresses (§9).
